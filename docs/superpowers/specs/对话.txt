当前结构已经是 feature-based（features/ + shared/），底子不错。我看主要有三个值得动的点，按优先级排：

1. shared/ 在膨胀成杂物间 — 已经有 api / components / config / events / storage / types / window 七个目录，未来还会更多。可以考虑两种方向：

引入轻量 FSD 分层：entities/（领域模型，如 Box、DesktopIcon）→ features/（用户操作）→ widgets/（组合视图）→ shared/（纯工具）。适合项目要长期演进。
或者按"平台 vs 业务"切：shared/tauri/（events + window + api 这些 Tauri 桥接）和 shared/ui/（纯 UI 工具），保持扁平。
2. 跨 feature 的耦合点没有清晰边界 — 比如 shared/types/desktop.ts、shared/config/desktopLayout.ts 其实是 desktop 这个 feature 的领域类型，被放到 shared 是因为 settings 那边也要用。这种情况说明缺一层 entities/ 来放可被多个 feature 共享的领域模型，比塞进 shared 更准确。

2.5. features/desktop/ 已经偏胖 — 里面同时有 store/ + components/ + config/ + utils/ + 多个 Window 相关组件。如果 Box 系统继续扩展，可以考虑把 BoxContextMenuWindow / DragPreviewWindow 这类独立的 Tauri 窗口抽到 widgets/ 或单独的 windows/ 顶层目录，因为它们其实是独立运行实例，不只是 desktop 的子组件。

主要 tradeoff：FSD 分层规范性强但前期会有"为了分层而分层"的负担，2 个 feature 的体量上 ROI 不高；按平台/业务切更轻，但长期可能还要再调一次。

# Dasktop Agent Notes

## 文件编码

- 读取、编辑、创建项目文件时必须使用 UTF-8 编码。
- 如果终端、工具或系统区域设置导致中文显示异常，必须优先怀疑读取/显示链路，不得直接认定源文件内容损坏。
- 涉及中文内容的修改应保持 UTF-8，不引入 GBK、ANSI 或其他本地编码。

## 注释规范

- 所有新增和修改的代码都必须补充符合阿里巴巴注释风格的注释。
- 注释应说明业务意图、设计原因、边界条件和非显而易见的实现逻辑，避免“赋值给变量”这类流水账注释。
- TypeScript、Vue 的公共类型、Store、组合式逻辑、跨模块函数和复杂交互必须使用 JSDoc。
- Rust 的 public struct、enum、function、module 和复杂逻辑必须使用 rustdoc 或必要的行内说明。
- TODO 注释必须写清楚责任、原因和后续处理方向，不允许留下模糊占位。

## 兼容与迁移

- 项目当前未上线，功能调整时不需要保留旧逻辑、旧字段、旧配置或旧数据结构的兼容分支。
- 旧逻辑必须直接删除，不做历史迁移脚本，不写兼容读取，不保留废弃配置入口。
